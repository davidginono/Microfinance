# Dashboard infolets

The 2026-10-22 increment adds an Oracle Financials-inspired pending-work section to the existing JSP dashboards. It keeps the navy/white shared shell, configurable dashboard layout and existing charts. Expanded infolets reveal a linked count breakdown; their reverse side contains optional age/amount display filters. These filters do not change credit policy, approval configuration or financial records.

Creation shortcuts are native links to existing creation pages, including ordinary vouchers, recorded loans/disbursements, receipt batches, payroll schedules/employers/instructions, account groups, activities, budgets and loan-adjustment requests when authorized. Client loan creation starts at the existing product selection page. Resources requiring a parent record retain their record-specific creation flow. Loan reviews, disbursement queues, guarantee requests and voucher statuses link directly to their existing authorized workspaces. No creation modal, simulated task page, duplicate approval form, or new posting command is introduced.

`GET /api/dashboard/work` returns read-only aggregates from the authenticated institution and selected branch. Request parameters cannot choose another scope. Client loan counts also require applicant ownership; pending guarantees require the authenticated guarantor and exclude superseded loans. Board, chairperson and credit-committee counts require a pending assignment for that reviewer and stage. Records without a first-class loan branch are not included by widening access.

Voucher infolets require the explicit voucher workspace claim and each visible voucher type's view claim. Incomplete voucher drafts, unvalidated vouchers, validation errors, pending approvals, ready-to-post vouchers, failed postings and rejected vouchers remain distinct. Validation, approval and posting are independent dimensions, so their status counts can overlap; the chart is not a unique-record total. Each status link uses the corresponding existing register filter. Pending approvals describe the authorized branch queue; they do not claim every item is assigned to the viewer. Readiness preserves validated + approval satisfied/not required + unposted semantics. Amounts are proposal/workspace totals, not ledger balances; guarantee amounts remain unavailable in this summary. Existing review/posting pages recheck every financial command.

The new endpoint performs bounded grouped queries, returns no full record lists and uses `Cache-Control: no-store`. It calls no external services and changes no database schema. Monetary aggregates retain database decimal precision and serialize as decimal strings. Display refreshes run only while the widget/page is visible, cancel stale requests and retain previous values with an error on a failed refresh; failures never become false zero counts. Display preferences contain no persisted financial data.

Charts and existing portfolio/credit widgets remain separate dashboard widgets. The pending-work chart uses the shared chart renderer, keyboard controls and accessible data alternative. Create and pending-work sections size to their content so expanded infolets and mobile controls remain visible.

Verification includes six scoped service tests, two MVC authorization/cache tests, four disposable PostgreSQL reporting tests, 24 dashboard JavaScript tests, and Jasper compilation of the client, staff, manager and admin dashboards. The full Maven suite also completed successfully; environment-gated tests remain skipped unless their dependencies are configured. Chrome checks of the authenticated accountant dashboard covered native receipt creation and loan-review queue navigation, inline expansion/filters, zero-data charts and layouts at 360, 768, 1366 and 1920 pixels without page-level horizontal overflow. Other roles' visibility and ownership are covered by service/SQL tests rather than claimed as live browser sessions. The 1,000 requests/second architectural target is not a measured throughput claim.
