# Configurable voucher approvals

The user-requested 2026-10-18 increment enables approval for individual ordinary receipt, payment and journal vouchers and for batches, independently per branch and voucher type. This supersedes the earlier prohibition on core approval steps **only where configuration enables them**. Unconfigured individual vouchers retain direct posting. Specialized loan repayment receipts and the existing loan collection batch worker retain their established ledger controls; they cannot enter this ordinary-voucher workspace.

## Screens and access

- `/finance/approval`: branch-scoped status tiles and a bounded, sortable register. Validation, approval and posting are independent columns. Select one row to open its details.
- Record details: permitted actions, approval route, field warning links, evidence and the latest 100 audit events. Approval never implies a posted journal.
- Voucher editor: dense editable lines, warning-to-field focus, scoped account lookup and read-only inspection for reviewers. Save returns to its parent; validation and submission operate on the complete workspace.
- `/finance/approval/configuration`: independent individual/batch switches, non-overlapping inclusive-minimum/exclusive-maximum TZS ranges, explicit automatic approval or up to two approver groups, and a saved-rule amount test. Journal batches use their largest voucher total; receipt/payment batches use the batch total. Gaps fail closed with a missing-rule error.

New claims appear in the existing access matrix. None are automatically granted. Workspace view/create/update/validate/post, initiate/withdraw/hold/approve/reject/force/senior approval, configuration view/configure, and document view/create are independent. Voucher-type view and creation claims still apply. Every command rechecks current claims, active staff access and institution/branch scope in the service. Reviewers cannot approve their own preparation; each sequential stage requires a different person. The administrator assigns claims; deploying this code does not activate approval or grant authority.

## Status and correction behavior

Oracle's [approval actions](https://docs.oracle.com/en/cloud/saas/financials/26d/fappp/considerations-for-approval-actions.html) inform the status semantics: Required → Initiated; withdrawal cancels eligibility for reviewer actions; Hold delays Required; resubmission starts a new review round after rejection, withdrawal, hold or material correction. Force approval requires both its dedicated claim and the enabled option, plus an audit reason, and produces Manually approved. Workflow approved and Manually approved remain separate from Posted.

Validation records field issues and a hash of resolved accounts, mappings and amounts. Editing unposted entries or adding evidence invalidates validation and prior approval. Content cannot change while approval is initiated; withdraw first. Configuration changes require validation and resubmission. Configuration revisions are retained as immutable evidence; each history event also preserves its policy version, assessed amount, statuses and review stage. Current account mappings and periods are checked again before posting. Approved content is not edited after posting: use existing linked voucher reversals.

Posting locks one envelope and commits every voucher, balanced journal, envelope link and audit together. Stable request keys and row locking prevent duplicate/concurrent posting. A failed attempt rolls back its financial writes; the controller records a separate recoverable failure status. Deferred database checks require every item in a posted envelope to be linked and validated and block direct inserts of individual vouchers when approval is configured. Historical posted request retries remain idempotent after configuration changes.

Supporting PDF/PNG/JPEG evidence is branch scoped, immutable, limited to ten files of up to 5 MB each, checked by file signature, served without caching, and protected by its own claims. There are no new exports; posted vouchers retain existing PDF/print.

## Supplied design increment

The supplied four designs now guide the register, rule builder and the two voucher-editor contexts. Five summary cards show incomplete-record age, recent creation/update activity, recorded validation issues, approval states and posting readiness. Ready means validated, approved (or approval not required) and not posted. The mixed-type register restricts its types to the viewer's claims; search, date range, status and sorting remain server-side. Selected-row approval commands retain the independent-review and current-version checks.

Configuration is under Settings, and approvals are under Accountant Office. The IF/THEN builder exposes the supported branch/type and TZS amount conditions, copy/remove controls and up to two required-response review stages. The approver dialog selects a claim group or a named eligible staff member in the current branch. Staff lookup is bounded and resolves candidate permissions in a batch. Validate checks configuration without saving it. Arbitrary condition expressions, FYI stages and institution-wide reviewer routing are not exposed as working controls.

The voucher editor separates header/line entry from supporting-document preview, shows warning links and inline field messages, and uses a sticky desktop action footer. Save stays in the editor; Save and close returns to its workspace. Validate saves corrections and checks the complete workspace. Only a single-voucher workspace can submit from the editor; batch editors return to the parent batch. Commands preserve their submitted values through the shared form submission lock. The existing scope, claim, audit and posting engine protections remain authoritative.

The status-card links and Clear update the existing table through the shared cancellable GET adapter. They retain current search/type/date/sort, reset pagination and selection, synchronize the category selector, heading, card counts and active green strip, and leave the page shell mounted. Redirected/failed requests retain the previous rows with a retryable table error; rapid filters cancel older requests. Ordinary modified link clicks retain browser behavior.

Supporting documents render locally with pinned PDF.js 6.4.299 (including its worker, fonts and licenses), without a third-party viewer or network service. A single PDF page is rasterized on demand with bounded pixel memory; page navigation and zoom are available. Image previews, loading and failure states retain the scoped original-file link. The original no-store, claim and tenant/branch checks and restrictive document response headers are unchanged.

Final design verification on 2026-10-18 passed 59 focused tests (22 PostgreSQL workflow, 14 MVC, one six-page JSP compilation, four workspace-security and 18 claim tests). The source/implementation comparison and evidence paths are recorded in the appended approval section of design-qa.md. ## Standalone creation workflow removed (2026-10-18)

The approval area is a review and correction queue. Its separate Create voucher workspace page, GET creation form, POST creation endpoint, creation DTO/service operation, Add voucher links and item-removal endpoint have been removed. Editor GET/POST routes accept existing scoped items only; a forged new item ID cannot create a draft or append to a batch. Dead creation/removal labels and styling were removed.

Normal receipt/payment/journal forms still capture individual approval drafts when configuration requires approval, and retain direct posting when approval is not configured. Existing single and batch records, claim checks, validation/corrections, approval configuration, history, documents and posting safeguards remain. This removal adds no replacement batch-creation flow and performs no data/schema deletion. Existing batch approval tests use direct disposable fixtures rather than a removed production API.

Verification: the focused working-tree run passed 44 tests (23 PostgreSQL workflow, 16 MVC, one JSP compilation covering the five retained voucher/approval pages, and four workspace-security tests). Browser checks with disposable synthetic records confirmed no creation link in the approval queue, no Add voucher link on batch details, existing warning/correction access and a contained 360-pixel page width. The preview was left running locally. Earlier design edits remain outside this removal commit.
