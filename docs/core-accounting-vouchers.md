# Core accounting vouchers

Receipt, payment and journal forms accept several configured activities. Each transaction row can use a transaction from any selected activity. Removing an activity clears its transaction selections and keeps amounts and descriptions. Saved drafts keep the selected activities. Staff with permission to edit a draft can choose a different transaction from those activities for each line.

Activity-scoped rows require a configured transaction; preview/post recheck activity ownership, active templates and accounts, money direction and existing loan protections. ## Resource structure

- `/finance/vouchers/receipts`, `/payments`, `/journals`: separate institution/branch-scoped registers, 25 records per page, date/search/status/sort filters and single-row selection. View/PDF/Print are enabled only for one selected record, with an independent Create action.
- `/{kind}/new`: focused full-page creation, primary header fields, optional context and 1–50 numbered transactions. Preview resolves balanced entries on the server without saving; Post creates all entries atomically. The header money account supplies the initial default for receipt/payment transactions. Add debit / Add credit switches an ordinary transaction to explicit entries, each with its own account and amount. Both sides must equal the transaction amount. Receipt debit entries and payment credit entries may use several eligible cash/bank/mobile-money accounts; their other side remains non-money accounts. Configured templates stay fixed unless the staff member explicitly chooses manual accounts. Specialised loan receipts retain their separate allocation flow.
- `/{kind}/{id}`: immutable document details, account snapshots, exact TZS totals, poster/time, PDF, printable document, and linked direct reversal. Reversals preserve original evidence and swap all entries, not overwrite them. The authorized accountant may reverse their own posting; there is no checker requirement.
- `/{id}/pdf` and `/{id}/print`: authorization and branch scope are checked again. Both now use the same embedded-font A4 PDF layout with monochrome institution/branch identity, transaction/account columns, exact totals, amount in words, narration, posting identity, repeated headings and page numbers. Print uses the browser PDF viewer rather than a separate HTML print layout. See [accounting document formats](accounting-document-formats.md) for the supplied screenshot references and financial-report formats.

## Posting boundaries

All monetary arithmetic is decimal, server-calculated and limited to two fractional digits. Each transaction creates a debit/credit pair. Both journal and voucher are append-only and must agree. A stable request key with exact payload/actor matching returns the original posting on retries; changed payloads are rejected. Receipt/payment references are unique within the branch and money account. A linked reversal is permitted once. Audit failure rolls the entire transaction back, including outbox and document records.

Accounts are active, institution-scoped ordinary `POSTING` accounts, not headings or loan controls. Receipts debit a CASH/BANK/MOBILE_MONEY account; payments credit it. Transfers between money accounts use journals. Configured transaction templates may be selected per row/component; mappings are resolved and locked on the server, the selected template revision must still match, and the actual account names/codes are snapshotted. No client-supplied total, mapping or approval is authoritative.

An existing open accounting period is shared-locked while posting. When no period covers the date, core accounting creates a one-day open period under the existing setup advisory lock; it cannot post in a closed period or open a date before a later close. Direct journals have a distinct `direct_post`/`CORE_*` identity and no invented policy/checker records. Historical policy-backed journals keep their existing constraints.

Ordinary vouchers do **not** post loan repayments/disbursements, calculate fees, reconcile bank channels, establish historical opening balances, or certify financial statements. The receipt form now has an explicit Loan repayment purpose for directly recorded loans: it delegates to the owning loan services and creates an immutable document envelope, not another GL journal. These receipts require loan permissions and complete independent corrections, unlike ordinary voucher reversals. See [unified receipts](unified-receipt-vouchers.md). These features do not finish the larger accounting/report-builder checklist. Branch display uses the existing branch location, with branch ID fallback because the current branch entity has no dedicated display-name field.

## Permissions and output policy

Core voucher access uses existing BUSINESS_VIEW/CREATE/REVERSE and JOURNALS_VIEW/CREATE/REVERSE claims; PDF/print additionally require FINANCIAL_REPORTS_EXPORT. Active accountant defaults and existing materialized accountant claims receive these capabilities in V55. Current permissions/workspace status are rechecked in services; subsequent explicit revocation remains effective. No lending claims are granted.

Accounting/report exporters and queued report requests accept only PDF. Retained CSV/XLSX enum values identify historical records, not enabled output formats. Historical non-PDF downloads are blocked rather than deleting retained evidence. Existing import formats are not exports and are not changed by this policy.

## Split entries (18 November 2026)

V169 preserves existing pair transactions and stores new split entries separately with frozen account codes/names. The shared posting view reads both formats. There are at most 50 transactions, 50 entries per transaction and 500 journal entries per voucher. Preview, approvals, posting and linked reversal use the same exact-decimal entry plan; the voucher total counts each transaction once. Legacy form and plan hashes remain compatible for pending approvals and retries. Each money account reserves the payment/document reference, including conflicts with historical ordinary vouchers. Database guards require every transaction to balance and its immutable entries to match the posted journal.

Ordinary transaction setup now records a single TOTAL pair under MANUAL_JOURNAL without asking for an event or amount component. Existing specialised classifications remain stored and usable; their existing component identities cannot be replaced through the simplified setup. Account selectors use the shared bounded search and apply money-purpose filters before paging. Group headings are not posting accounts, and this change never changes account purposes or grants financial claims.

V170 allows existing purpose-OTHER posting accounts in the institution's designated Cash and Bank family, using the same active ASSET/POSTING eligibility as loan funding. Other-purpose accounts elsewhere remain ineligible; account purposes and versions are never rewritten.

Apply the forward migrations with a verified deployment backup. Verification uses disposable PostgreSQL databases; the operational server is not changed by the source update.

Activity and transaction codes are generated on the server as ACT-000001 and TXN-000001 within each institution. V171 preserves existing codes, advances counters past matching existing codes, and records request keys/hashes so concurrent retries keep the same new record. Code fields are absent from creation forms; transaction setup selects an existing activity by name/code.

Manual entry uses repeatable debit/credit entries with an amount beside each account. Its hidden transaction total is derived from debit entries and is checked against both sides by the existing server plan. Configured activities alone show the transaction picker and an editable transaction amount; loan repayment keeps its specialised amount and allocation path.

Every receipt, payment and journal transaction must have equal debit and credit totals, each matching its transaction amount exactly. Initial server validation rejects a difference before account lookups or approval routing; the posting plan and database guard enforce the same rule again. Differences cannot cancel between transactions or between vouchers in a batch. Incomplete drafts remain editable, but cannot pass validation, enter approval or post until corrected. Existing posted evidence and specialised loan-repayment posting are unchanged.
