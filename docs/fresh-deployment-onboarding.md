# Fresh deployment and administrator handover

Database migrations create only the platform identity `ADM001`; there is no usable shared/default password. V134 disables the historical seeded password without changing administrators who already chose a different password.

1. Set `APP_BOOTSTRAP_ADMIN_PASSWORD` to a private random temporary password (at least 14 characters, no more than 72 UTF-8 bytes) in the deployment's secret environment. Never put it in Git, logs, a public document, a command-line argument or a URL.
2. Configure the production profile, database, protected upload storage and `APP_BASE_URL` (the deployed HTTPS address). Configure SMTP and its sender, and remove test recipient overrides. If settings are managed in the UI, configure and test them after administrator setup and before invitations.
3. Start the application. The startup service installs the temporary credential only for the still-uninitialized seeded identity. It never resets a chosen password on subsequent restarts. Without the environment secret the old credential remains unusable.
4. Open `/system-admin/login`, sign in as `ADM001` with the temporary password, and complete the mandatory administrator setup. Enter the administrator's name, email and phone, and a different new password (at least 14 characters). Setup blocks other authenticated operations, preserves CSRF and accepts only the platform administrator with the explicit platform-settings permission. Completing setup ends that session; sign in with the new password.
5. Remove `APP_BOOTSTRAP_ADMIN_PASSWORD` from the environment/secret store. Keep the permanent password in the administrator's password manager. Initial provisioning sets only this administrator's login/approval OTP preferences off so missing SMTP cannot lock out setup. Configure and test delivery, then enable the administrator's preferred OTP security through the existing settings. Add contact verification separately; entering contact details does not assert their verification. Existing administrators' preferences are unchanged.
6. Test platform email delivery, register the institution and at least one branch, then invite each branch's Institution Admin. Activation emails must be accepted by the configured SMTP server before account creation/resending reports success. SMTP acceptance is not proof of inbox receipt; confirm receipt during onboarding. A mail failure propagates and rolls back the invitation command, so retry after correcting delivery settings.
7. Institution Admins activate their invitations, create staff and assign the required explicit permissions. New staff activate using the emailed link and OTP, then set their own password. The default invitation lifetime is 72 hours. Existing clients assigned staff access use their separate acknowledgement flow.
8. Configure approved lending products/routing, credit controls and accounting arrangements before lending. Explicitly assign client-onboarding permissions and independent reviewers. Enable the branch's KYC gate when ready.

## Explicit whole-deployment reset

A reset is maintenance, never an application page or an automatic migration. Stop the intended deployment and all workers first. Verify the exact database host/name and upload roots. Take a protected recovery backup when retention is intended. Recreate only that application's schemas/database and run all immutable Flyway migrations normally; this avoids bypassing financial-history triggers with ad hoc row deletion. Remove that deployment's user-upload directories and persistent sessions only after checking their resolved paths. Do not use the old partial operational reset script for a clean V134 deployment: it preserves users/settings and predates the immutable ledgers and KYC evidence.

After reset, verify zero institutions/branches/clients/staff/invitations/loans/journals/uploads, exactly the seeded `ADM001`, current migrations and `platform_setup_required=true`. Provision a private temporary password as above. Static application assets and seeded accounting reference definitions are code/configuration, not user history.

The setup gate reads the session principal, adding no request database lookup. Completion uses one locked platform identity and a bounded contact-conflict check in a short audited transaction. SMTP remains bounded by the existing configured timeouts; invitation sending retains its existing transaction and retry behavior. No throughput benchmark is implied.
